对任务的实现评估

一、总体判断

这个项目不是从零开始，已经具备 FastAPI 后端、Vue 前端，以及数据集、模型、预测、评分等页面和接口雏形。

但从现有代码看，很多功能目前还停留在“页面/接口已存在，核心业务链路未完全打通”的状态。真正要实现任务.txt里的需求，难点主要不在页面按钮，而在“用户动态上传的数据集、模型文件、训练脚本、checkpoint、预测结果、评分指标”之间建立一条稳定、可追踪、可复现的闭环。

现有基础：
1. 数据管理已有上传、下载、查看、删除接口和页面。
2. 模型管理已有 .py 模型上传、训练按钮、训练文件上传/下载、数据校验入口。
3. 预测管理已有方案列表、详情页、部分 EPF 预测结果读取逻辑。
4. 评分管理已有评分汇总接口和前端表格。

主要缺口：
1. 用户上传模型后的真实训练和真实预测没有完整执行链路。
2. checkpoint 与模型、数据集、训练任务、预测任务之间的关联还不完整。
3. 数据集校验目前更像“上传数据 vs 基础表”的校验，不完全符合“用户随时上传的两个 CSV 数据集互相比对”的需求。
4. 预测和评分页面目前大量依赖已有 EPF 结果文件或兜底数据，不是完全由本次用户选择的模型和数据动态生成。

二、实现难点

1. 动态上传数据集的结构约束

任务要求上传“结构良好的 CSV”，但需要明确 CSV 的标准结构。现在后端已有 CSV/Excel 解析逻辑，但字段映射、时间格式、必填列、可选列、编码、缺失值、重复时间点、单位等规则需要定死。

如果不先定义标准，后面训练、预测、评分都会不稳定。例如同样是电价字段，可能叫 price、price_kwh、电价、实际电价；时间字段也可能有日期、小时、完整时间戳几种写法。

难点在于：上传文件不是只保存文件，还要解析为统一的数据表，并保证后续模型训练能直接使用。

2. “两个动态上传数据集”之间的校验逻辑

任务中特别强调：两个数据集都是用户随时上传、随时变化的。

现有代码里数据集校验更偏向把某个上传数据集和 BasePriceData 基础数据做比较。这和需求有差异。需求更像是：
- 数据管理页面已有一个平台数据集 A；
- 模型管理页面上传一个训练/校验数据集 B；
- 点击“数据集校验”时比较 A 和 B 是否完全一致。

这里需要补充比较规则：
- 是否要求行顺序完全一致，还是按时间字段排序后比较；
- 浮点数是否允许误差；
- 是否比较所有列，还是只比较核心列；
- CSV 表头顺序不同但字段相同算不算一致；
- 空值、编码、日期格式不同但语义相同算不算一致；
- 校验失败时是否需要返回差异明细。

如果只是返回“通过/失败”实现较简单；如果要返回差异行、差异列、缺失记录、额外记录，工作量会明显增加。

3. 用户上传 .py 模型的安全执行

模型管理页面要求支持上传 .py 文件，并点击训练模型。这个难点很大，因为上传的 Python 文件本质上是任意代码。

需要考虑：
- 允许模型文件暴露什么入口函数或类，例如 train(input_csv, output_dir) / predict(checkpoint, input_csv, start, end)；
- 是否允许用户代码访问文件系统、网络、环境变量；
- 训练超时、内存限制、异常日志如何处理；
- 多个用户或多个任务同时训练时如何隔离；
- 依赖包如何安装和管理；
- 训练失败后如何把错误展示给前端。

当前代码的 train_model 主要读取已有 EPF 结果指标，并没有真正执行用户上传的 .py 模型。prediction_service 里也有 TODO，用户模型预测值目前不是从上传模型或 checkpoint 计算出来的。

4. checkpoint 生命周期管理

任务要求训练输出 checkpoint，后续预测页面可以拿这个文件预测，也可以下载训练文件。

这里需要设计 checkpoint 的数据模型和文件管理：
- 一个模型是否可以有多个训练版本；
- 每次训练对应哪个数据集、训练日期范围、脚本版本；
- checkpoint 文件类型是什么，pt/pth/pkl/dill/joblib/onnx 是否都支持；
- checkpoint 是否和 scalers、配置文件、特征列清单一起保存；
- 下载的是单个 checkpoint 还是打包 zip；
- 预测时如何选择某个 checkpoint，而不是只选择模型名称。

目前已有 trained-files/upload/download，但更像“按模型名保存最新文件”，还不够支撑可追踪的训练版本。

5. 训练脚本与项目接口的适配

任务说“训练脚本已经提供了”，但项目里有 epf、market 等脚本和产物，尚需确认本次要接入的是哪个训练脚本。

需要把脚本封装成后端可调用的统一命令或 Python API：
- 输入：训练数据 CSV、模型 py 文件、训练起止日期、输出目录；
- 输出：checkpoint、metrics、预测结果 CSV、日志；
- 状态：排队中、训练中、成功、失败；
- 日志：前端可查看或失败时可下载。

如果训练脚本目前只能在某个固定目录、固定文件名、固定环境下运行，则接入动态上传数据集会比较麻烦，需要先改造脚本参数化。

6. 预测页面动态化

任务要求预测页面可以选择不同模型、日期范围，并按项目已有维度可视化出图，且图表内容随预测结果动态变化。

现有预测页面已有列表和详情，但新建方案弹窗目前没有完整提交逻辑，部分展示还使用 localStorage 或已有 EPF 文件。要真正动态化，需要后端新增或完善“预测运行”流程：
- 用户选择模型/checkpoint、数据集、起止日期；
- 后端执行 predict；
- 保存每个时间点的预测结果；
- 保存图表需要的统计维度；
- 前端根据接口返回的数据渲染图，而不是读取固定文件或固定展示。

难点在于不同模型的预测输出格式必须统一，否则评分和可视化很难复用。

7. 评分管理的指标口径

任务要求对不同模型评分并可视化。现有评分服务已有 MAE、RMSE、R2、IMAPE、score 等计算和 EPF fallback，但需要确认最终评分规则。

需要明确：
- 分数公式是什么；
- 是否以实际电价为基准；
- 是否按日期、负荷、风速、天气、节假日等维度分组；
- 是否要求模型排名；
- 是否要比较 Base 模型和用户模型；
- 评分是预测完成后自动生成，还是评分页面点击计算。

如果指标口径不明确，后续很容易出现“功能做完但结果不被认可”的问题。

8. 前后端数据模型需要收敛

目前前端页面里有一些字段是前端临时拼出来的，例如模型管理里的校验状态被写成固定“校核通过”；预测列表的时间段来自 localStorage；评分页强制 source=epf。

要实现真实业务，需要后端成为唯一数据源：
- 模型状态来自数据库；
- 数据集校验状态来自数据库；
- 训练状态来自任务表；
- 预测时间段来自预测运行记录；
- 评分结果来自预测结果计算。

否则页面看起来能操作，但刷新、换数据、换模型后状态会不可靠。

9. 编码和中文显示问题

当前读取到的多个源码文件中中文字符串显示为乱码形态，可能是终端编码问题，也可能是文件内容已经被错误编码保存。正式开发前需要确认源码文件编码统一为 UTF-8。

如果文件本身已经乱码，需要先修复中文文案，否则前端页面和接口错误信息会继续显示异常。

三、还需要需求方提供或确认的内容

1. CSV 标准模板

必须提供至少一份标准 CSV 样例，并明确：
- 必填列；
- 可选列；
- 时间格式；
- 数值单位；
- 编码格式；
- 缺失值处理规则；
- 是否有多时区或跨天数据。

2. 数据集校验规则

需要确认两个 CSV 比对时：
- 是否要求完全字节级一致；
- 是否按业务字段比较；
- 是否允许浮点误差；
- 是否忽略列顺序；
- 是否忽略行顺序；
- 校验失败是否需要差异报告。

3. 模型 .py 文件接口规范

需要提供模型文件必须实现的函数或类，例如：
- train(train_csv_path, output_dir, config) -> checkpoint_path
- predict(checkpoint_path, input_csv_path, start_date, end_date, output_dir) -> prediction_csv_path

同时需要提供一份可运行的示例模型文件。

4. 训练脚本位置和运行方式

需要明确“已经提供的训练脚本”是哪一个文件，以及：
- 运行命令；
- Python 版本；
- 依赖包；
- 输入参数；
- 输出文件；
- 运行时长；
- 是否需要 GPU；
- 是否可并发运行。

5. checkpoint 格式

需要确认首期只支持哪种格式：
- .pt/.pth；
- .pkl；
- .dill；
- .joblib；
- .onnx；
- 或 zip 包。

建议第一期只支持一种标准格式或 zip 包，避免预测加载逻辑过早复杂化。

6. 预测结果标准格式

需要确认预测脚本输出 CSV 的字段，例如：
- record_time；
- actual_price；
- predicted_price；
- model_name；
- quantile 或置信区间字段；
- 负荷、天气等维度字段是否随结果输出。

7. 可视化维度

任务里说“按照项目展示的几个维度”，需要明确最终需要哪些图：
- 按时间序列展示实际值/预测值；
- 按日期范围聚合；
- 按负荷分组；
- 按天气分组；
- 按风速分组；
- 按模型对比；
- 是否需要置信区间或分位数曲线。

8. 评分公式和排序规则

需要确认：
- score 的计算公式；
- MAE/RMSE/R2/IMAPE 是否都要展示；
- 是否分维度分别评分；
- 是否每次预测后自动评分；
- 排名升序/降序规则；
- 极端值、实际值为 0 时如何处理。

9. 任务执行方式

训练和预测都可能耗时，建议确认：
- 是否需要异步任务；
- 前端是否需要进度条；
- 是否需要训练日志；
- 是否允许同时跑多个任务；
- 任务失败后是否允许重试。

10. 权限和安全边界

上传并执行 .py 文件风险很高。需要确认是否只是内网可信用户使用。如果不是，必须增加沙箱、白名单、隔离运行目录、超时限制、依赖限制等安全措施。

四、建议实施顺序

第一阶段：把数据集能力做扎实
- 统一 CSV 模板；
- 修复数据集上传、查看、下载；
- 实现两个动态数据集的可配置校验；
- 校验失败返回清晰原因。

第二阶段：定义模型接口和训练产物
- 明确 .py 模型入口规范；
- 建立训练任务表和 checkpoint 版本表；
- 后端可以执行训练脚本；
- 前端能查看训练状态、日志、下载 checkpoint。

第三阶段：打通预测闭环
- 选择模型版本/checkpoint；
- 选择数据集和日期范围；
- 执行预测；
- 保存预测结果；
- 前端图表完全使用预测结果动态渲染。

第四阶段：评分和可视化
- 基于预测结果计算评分；
- 支持不同模型对比；
- 按日期、负荷、风速、天气等维度展示；
- 排名和图表都从后端评分结果生成。

五、工作量判断

如果只是补页面按钮、上传文件、简单比较 CSV、读取已有结果文件，工作量中等。

如果要实现“用户动态上传模型 -> 后端真实训练 -> 产出 checkpoint -> 动态预测 -> 动态评分可视化”的完整闭环，难度较高，主要是后端任务执行、模型接口规范、文件版本管理和安全隔离。

在现有项目基础上可以做，但需要先补齐上面列出的输入规范。尤其是模型文件接口、训练脚本运行方式、checkpoint 格式、预测结果格式，这四项不明确的话，实现过程中会反复返工。

六、关于“两个动态上传数据集之间的校验逻辑”的补充核查

进一步看代码后，项目里确实已经有“数据集校核”功能入口，但当前实现不是严格意义上的“两个动态上传数据集互相比对”。

现有相关位置：
- 后端校核入口：backend/app/api/routes/datasets.py
- 前端模型页调用：frontend/src/views/ModelsView.vue
- 前端 API 封装：frontend/src/api/datasets.ts

当前实际流程是：
1. 在模型管理页面点击“数据集校核”。
2. 前端先上传一个数据集文件，调用 /datasets/upload。
3. 上传成功后，再调用 /datasets/{dataset_id}/verify-async。
4. 后端 _verify_dataset_internal(dataset_id) 会读取这个上传数据集在 DatasetRecord 表里的记录。
5. 然后读取 BasePriceData 表里的基础电价数据。
6. 按 record_time 做匹配，只比较 price_kwh 和 load_kw 两个字段。
7. price_kwh 和 load_kw 的允许误差是 0.01。
8. 最后把数据集 verify_status 设置为“校核通过”或“校核失败”。

也就是说，当前逻辑更准确地说是：
“用户上传的数据集” vs “系统基础电价数据 BasePriceData”。

它不是：
“数据管理页面已有的某个用户上传数据集 A” vs “模型管理页面新上传的某个用户数据集 B”。

代码里还有一个 compare_records(new_records, existing_records) 函数，看起来像是用于比较上传记录和已有记录。它会按 record_time 排序后比较 record_time 和 price_kwh，误差阈值是 0.001。但是搜索后没有发现它被实际调用，所以目前不能算已经接入业务流程。

还有一个需要注意的点：/datasets/upload 上传时，如果发现同名数据集，当前逻辑会删除旧 DatasetRecord 并用新数据覆盖。因此如果模型页校核时填写的是已有数据集名称，它可能不是拿“新上传数据”和“原已有数据”做比较，而是先覆盖原数据，再拿覆盖后的数据去和 BasePriceData 校核。这和“两个动态上传数据集互相比对”的需求不一致。

所以这部分评估应更新为：
项目中已有数据集校核雏形，但当前主要是“上传数据集 vs 基础数据表”的校核；不满足完整的“两份动态上传 CSV 数据集之间互相比对”。如果需求明确要求两份动态数据集互相比对，需要新增或调整接口，例如：
- 指定 source_dataset_id 和 target_dataset_id；
- 或上传临时校验文件但不覆盖原数据集；
- 后端按明确规则比较两份 DatasetRecord；
- 返回校核状态，并最好返回差异行数、缺失记录、额外记录、字段差异等明细。

七、根据补充信息形成的后续实现流程

你补充的信息已经能把需求进一步收敛成一套可执行方案：
1. 标准 CSV 格式以 epf/ensemble/广东电价数据.csv 为准。
2. 数据集校验先按项目已有校验规则实验可行性。
3. 模型文件参考 epf/ensemble/epf_predict.py 现有写法，需要设计统一接口规范。
4. 训练脚本当前没有，需要新增一层后端训练脚本/训练服务。
5. checkpoint 交付格式用 zip 包。
6. 预测结果格式先沿用现有脚本输出格式，用现有可视化逻辑消费。
7. 评分界面先按现有格式输出。
8. 指标展示 MAE、RMSE、R2、IMAPE，score 按项目已有评分方式设计，降序排序，不额外处理特殊情况。
9. 训练、预测都需要异步任务、进度、日志、并发、失败重试。
10. 上传 .py 的安全隔离暂时不用处理。

1. 标准 CSV 格式

标准 CSV 表头确认如下：

时间,电价(元/kWh),负荷(kW),温度(℃),风速(m/s),云量(%)

示例数据：

2022/1/1 0:00,372.8917,40456,15,1,0
2022/1/1 0:15,393.635,40143,14.5,1.5,0

后续实现时建议统一映射成后端内部字段：
- 时间 -> record_time
- 电价(元/kWh) -> price_kwh
- 负荷(kW) -> load_kw
- 温度(℃) -> temperature
- 风速(m/s) -> wind_speed
- 云量(%) -> cloud_cover

这和现有 DatasetRecord / BasePriceData 的字段基本匹配。数据上传、校验、训练输入、预测输入都应该使用这一套字段映射，避免每个模块各自解析 CSV。

需要注意：当前 epf/ensemble/epf_predict.py 里读取列名的字符串看起来可能存在编码错位，和标准 CSV 表头不完全一致。后续接入前必须先运行一次脚本验证它能否直接读取 epf/ensemble/广东电价数据.csv。如果不能，需要先修复脚本里的列名，或在训练服务里生成一份脚本可识别的中间 CSV。

2. 数据集校验的可行性实验

可以先按现有校验规则做实验，结论要分两层：

短期可行：
- 先把标准 CSV 导入为 DatasetRecord；
- 再把同一份或同结构标准数据导入 BasePriceData；
- 调用 /datasets/{dataset_id}/verify 或 /datasets/{dataset_id}/verify-async；
- 如果 price_kwh 和 load_kw 在相同 record_time 下误差小于 0.01，则校核通过。

现有校验规则的实际含义：
- 比较对象：DatasetRecord vs BasePriceData；
- 匹配键：record_time；
- 比较字段：price_kwh、load_kw；
- 误差阈值：0.01；
- 输出：数据集 verify_status = 校核通过 / 校核失败。

这可以用于验证“用户上传训练数据是否和平台基础数据一致”。

但如果要完全符合“两份动态上传数据集互相比对”，还需要补充：
- compare_dataset_id 和 target_dataset_id 两个参数；
- 或者模型管理页上传临时校验文件，不覆盖原数据集；
- 比较 DatasetRecord vs DatasetRecord；
- 可选返回差异明细。

建议第一步先保留现有 BasePriceData 校验规则跑通，因为它和现有代码最贴近；第二步再扩展为两个 DatasetRecord 之间的动态比较。

3. 模型文件接口规范设计

现有 epf/ensemble/epf_predict.py 是命令行脚本风格，已经支持：
- --data：输入 CSV 路径；

7. 评分规则

项目当前已有评分公式，建议沿用：

IMAPE 单点计算：
- actual_floor = max(abs(actual), 150.0)
- predicted_floor = max(abs(predicted), 150.0)
- denominator = max(actual_floor, predicted_floor)
- ape = abs(actual - predicted) / denominator
- imape_point = min(ape, 1.0)

整体 IMAPE：
- imape = mean(imape_point)

score：
- score = max(0, min(100, (1 - imape) * 100))

其他指标：
- MAE = mean(abs(predicted - actual))
- RMSE = sqrt(mean((predicted - actual)^2))
- R2 = 1 - SS_res / SS_tot；如果 SS_tot 过小则为 0。

排序：
- score 降序；
- 如果分数相同，可以按 imape 升序或样本数降序作为辅助排序，沿用项目现有逻辑即可。

展示：
- MAE、RMSE、R2、IMAPE、score 都展示；
- 评分界面先按现有表格和筛选维度展示；
- 图表可以先复用现有预测结果的时间序列/区间图，不额外扩展复杂图。

8. 异步任务、进度、日志、并发、失败重试

训练和预测都应该走异步任务。

建议流程：
1. 前端点击“训练模型”。
2. 后端创建 task，状态 pending。
3. 后端后台执行训练，状态 running。
4. 训练过程中写 task_log 或 logs.txt。
5. 前端轮询 /tasks/{task_id} 和 /tasks/{task_id}/logs。
6. 成功后状态 completed，返回 checkpoint.zip、metrics、artifact 列表。
7. 失败后状态 failed，保留错误信息，允许点击“重试”。

并发建议：
- 第一版可以做简单队列或限制同时运行数量；
- 同一个 model_id 同一时间只允许一个训练任务；
- 不同模型可以并发，但要注意 GPU/CPU 资源；
- 每个任务必须有独立 run_dir，避免文件互相覆盖。

重试建议：
- 重试时新建 task，不覆盖旧 task；
- 可以复用同一模型和数据集参数；
- 旧失败日志保留。

9. 推荐的完整业务流程

第一步：上传平台标准数据集
- 数据管理页面上传标准 CSV；
- 后端解析并入库 Dataset / DatasetRecord；
- 必要时同步导入 BasePriceData；
- 页面可查看记录。

第二步：上传模型文件
- 模型管理页面上传 .py；
- 后端保存模型文件，记录 model；
- 校验脚本是否满足命令行接口规范，可以先做静态检查或 dry-run。

第三步：上传/选择训练数据并校核
- 模型管理页面选择已有数据集或上传校核数据；
- 第一版调用现有 BasePriceData 校核；
- 后续扩展为 dataset_id A vs dataset_id B 的动态校核；
- 校核通过后允许训练。

第四步：训练模型
- 前端点击训练；
- 后端创建异步 task；
- 后端导出标准 input.csv；
- 调用模型脚本；
- 解析输出；
- 打包 checkpoint.zip；
- 保存训练指标、日志、产物；
- 前端展示训练状态并允许下载 checkpoint.zip。

第五步：预测
- 前端选择模型/checkpoint、数据集、日期范围；
- 后端创建 prediction_run；
- 如果 checkpoint 可执行 predict，则调用 predict；
- 如果第一期只支持 train_predict，则使用训练输出的 predictions_week0.csv / predictions_test_full.csv；
- 后端解析 time、true、q0.5 等字段，写入 PredictionRunRecord；
- 前端按现有格式可视化。

第六步：评分
- 后端从 PredictionRunRecord 读取 actual/predicted；
- 计算 MAE、RMSE、R2、IMAPE、score；
- 写入 PredictionRun；
- Ranking 页面按现有格式读取 summary；
- score 降序展示。

10. 目前还需要确认或特别注意的问题

剩余问题不多，但有几项会影响实现顺序：

1. epf_predict.py 是否能直接运行标准 CSV。
   标准 CSV 表头是正常中文，但脚本里的列名字符串看起来可能编码错位。需要先实际运行验证。如果不能运行，要先修复列名读取。

2. checkpoint.zip 是否必须支持后续单独预测。
   如果只是下载训练产物，当前脚本输出打包即可；如果预测页面必须上传/选择 checkpoint.zip 后重新预测，则脚本需要额外保存模型权重和 scaler，并提供 predict 模式。

3. 第一版预测是否允许直接使用训练脚本产出的 predictions_week0.csv。
   如果允许，实现最快；如果必须根据任意用户选择日期范围重新预测，需要改造脚本支持 start_time/end_time 和 checkpoint 加载。

4. BasePriceData 的来源要固定。
   既然第一版先按已有校验规则实验，就要明确 BasePriceData 是由哪份标准 CSV 初始化，避免校核时基础表为空或不是同一份数据。

5. 同名数据集上传覆盖问题要处理。
   如果模型页上传校核数据时使用已有数据集名称，当前逻辑可能覆盖旧数据。建议后续实现时增加“临时校核上传”或显式 compare_dataset_id，避免误删原数据。

6. 任务并发策略需要有默认限制。
   你说需要并发、进度、日志、失败重试，但第一版最好限制同一模型同时只能训练一个任务，防止输出目录和 GPU/CPU 资源冲突。
